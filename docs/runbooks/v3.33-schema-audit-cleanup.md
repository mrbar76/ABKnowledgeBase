## What happened

`/api/health/ingest` had been silently failing on every Apple Health
workout INSERT/UPSERT for months. The SQL referenced `pace_avg`,
which was DROP'd in v1.9.4. Postgres raised `column "pace_avg" does
not exist`; the route handler caught it at `routes/health.js:1074`
and only logged to stderr. No surfacing, no alarm, no metric.

Adjacent failure: `workouts.adjustment` had been DROP'd in db.js
but the boot DROP was silently failing every restart because
`update_workouts_search()` trigger pinned `NEW.adjustment`. The
`safeQuery` wrapper swallowed the dependency error.

Both bugs hid because **`safeQuery` had no surface other than stderr**,
and nobody read stderr unless prompted.

## Open question surfaced by the coverage audit (HIGH severity)

**Gap #1 — forward-going movement after the Aug 5 `daily_activity` drop.**

`POST /api/v2/daily-vitals` only accepts 4 fields (`hrv_ms`,
`rhr_bpm`, `sleep_total_min`, `respiratory_rate_bpm` — see
`routes/v2-vitals.js:20-24`). Movement metrics (steps, distance,
exercise_minutes, flights_climbed, active/basal energy, workout_count)
flow ONLY via `daily_activity` from HAE today.

v3.34 #2 absorbs historical data into `daily_vitals_cache` but does
NOT establish a new forward-going write path. After the Aug 5 drop of
`daily_activity`, the 7 new columns will contain backfilled history
and then stop receiving new data.

Two paths to close before Aug 5:
1. **Extend the iOS Shortcut + `validateBody` in `v2-vitals.js`** to
   POST the 7 movement+energy fields. Smaller code change; keeps the
   "Shortcut is canonical" architecture intact.
2. **Keep HAE ingest alive post-Aug 5** specifically for these fields,
   rerouted to write `daily_vitals_cache`. Larger change.

Operator decision required before Aug 5.

## Audit mandate going forward

The wide-table problem (`daily_context`, `workouts`) wasn't only about
attribute slots — it let fields go silently missed because there was
no clean home for them and no signal when expected data wasn't
arriving (the HRV/RHR/respiratory-rate pipeline that was never wired
is the canonical example). The principle for every future schema
change:

> Every source, every field it emits, every captured column, every
> gap — all visible in `docs/SCHEMA.md`. "Is anything being missed?"
> must be a table the operator can read.

The coverage map section in `SCHEMA.md` is the standing artifact;
update it whenever a new source is wired or a column added/dropped.

## What the system now guarantees that it didn't before

1. **`/diag/deprecated-columns` is the green-light invariant.**
   `schema_drift_count: 0 && failed_migrations_count: 0` means live
   schema matches intent AND no boot migration silently failed.
2. **Every DROP has a manifest entry.** Tests in
   `tests/phase2-schema.test.js` enforce that every
   `safeQuery('<table> -<col>', ...)` in `db.js` has a
   `DEPRECATED_COLUMNS` row in `routes/health.js`.
3. **Snapshot-before-drop is the convention.** When a drop will lose
   data, the value is copied to `metadata.<legacy_key>` first. Two
   reference implementations: `workouts.adjustment → legacy_adjustment`
   (v3.33), `daily_plans.actual_exercises → legacy_actual_exercises`
   (v1.8.20).
4. **`safeQuery` no longer swallows in silence.** (Post follow-up PR.)
   Failures are pushed into an in-process log and surfaced by the
   sentinel. The exact failure mode that hid the adjustment-DROP bug
   for months would now show up as `failed_migrations_count > 0` at
   the first `/diag/deprecated-columns` hit.
5. **CI is enabled.** (Post follow-up PR.) `npm test` gates merges;
   integration job validates initDB + migration scripts against a real
   Postgres before any operator-triggered `--apply`.
